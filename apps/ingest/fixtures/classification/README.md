# Vendored classification fixture

The pruned trace-capture corpus that CI replays through the AI span classifier
(`src/ai_classification_fixture_test.rs`). Generated by trace-capture's
`bun run fixture` and copied here **verbatim** — all three files, unmodified.
Format spec: trace-capture `docs/classification-fixture.md`.

| file | purpose |
| ---- | ------- |
| `classification-fixture.jsonl` | one line per surviving corpus span — classifier inputs, negatives collapsed onto weighted representatives |
| `expectations.json` | per-capture aggregate goldens, copied verbatim from the reviewed seeds (see the caveat below) |
| `manifest.json` | counts + sha256s — the integrity/staleness anchor |

## Re-vendoring

Whenever trace-capture's `captures/` or any `frameworks/*/registry-seed.yaml`
changes, regenerate and re-vendor in the **same change** that adjusts
`src/ai_vendors.rs`:

```sh
cd ../../../trace-capture   # or wherever the checkout lives
bun run fixture
cp fixture/classification-fixture.jsonl fixture/expectations.json fixture/manifest.json \
   <maple>/apps/ingest/fixtures/classification/
```

The fixture test recomputes both sha256s against `manifest.json`, so a hand-edit
of the *fixture*, a partial re-vendor, or a line-ending mangle fails CI loudly.
**Nothing hashes `manifest.json` itself**, so editing a golden and pasting the new
sha into the manifest is self-consistent — which is exactly the edit a reviewer
most needs to catch. The defence is `manifest.source`: the trace-capture commit
(with a `dirty` flag), a hash over the sorted seed files and a hash of both
generator files.

Be precise about what that buys: `commit` re-derives the fixture only at
`dirty: false`, and today it is `false` — trace-capture's v2 work is committed, so
`git checkout <commit> && bun run fixture` over there reproduces these bytes. This
is provenance you can *replay*, not merely read. (Two structural defects had to be
fixed before `false` was even reachable: trace-capture's `fixture/` output dir was
untracked and un-ignored, so `git status --porcelain` was never empty; and
`generator_sha256` hashed one of the generator's two files.)

The test asserts `dirty == false` rather than type-checking the field, so a
re-vendor that reintroduces `true` fails. That is not a value to flip back: `true`
means the fixture came out of an uncommitted trace-capture tree, `commit` names a
revision that cannot produce these bytes, and the anchor is decorative. Commit over
there first, regenerate, re-vendor.

`manifest.dedup.value_sensitive_keys` is checked mechanically —
`value_read_keys_are_all_in_the_fixture_dedup_signature` re-derives every by-value
key read from `ai_vendors.rs` (the `attr`/`resource` accessors, plus every session
candidate's `key`/`event_key`, whose values decide session state) and fails if the
trace-capture-side list has fallen behind. That one matters more than it looks: a
missing key collapses spans that would classify differently onto one weighted
representative, which makes the FP numbers and the `slug/session_key_state`
histogram rows *wrong*, not merely lenient.

## What the line schema cannot express

Two rule shapes are outside this artifact, and the same test names both so neither
can ship unnoticed:

- **Scope attributes.** The line schema carries `scope_name`/`scope_version`/
  `scope_schema_url` but no `scope_attrs`, so a rule using `SpanCtx::scope_attr`
  could not be gated here. There are none today and the test asserts that; the
  first one needs a trace-capture line-schema extension and a `format_version`
  bump before it lands.
- **Link contents.** `links_count` is arity only — no link attributes, no linked
  ids — and the classifier exposes no link accessor at all, so the field is
  currently **unread** on this side. It stays in the schema because removing it
  would churn the artifact for nothing; a rule reading a link needs the same
  schema bump.

A maple PR touching vendor rules without a fixture bump (or vice versa) is still
the review smell to catch — there is deliberately no cross-repo network check;
maple CI stays hermetic.

## Expectations are never produced by *this* classifier

`expectations.json` is transcribed from the seeds' `goldens.per_capture`. Be precise
about what that buys: those numbers are produced by
`verify-seed.ts --emit-goldens`, i.e. by applying each **seed's own** rules to its
captures, and then human-reviewed (`goldens_status`). So a green replay proves
transcription fidelity — maple's Rust rules compute what the reviewed seed rules
compute — not ground truth. That is still the strongest gate available and it is
genuinely independent of this crate.

The exception is marked: six golden **fields** across four captures carry a
`v2_resolved: {fields, why}` declaration, meaning the shipped rule is outside the
seed algebra, so the seed evaluator cannot reproduce them and the number was
predicted by hand. The replay test asserts that set by `capture.field` so it cannot
grow silently — a field joining it is a golden losing its seed-side check.

This replay is the only check for four of the six. The other two have weaker gates
and nothing else says so:

| field | gate |
| --- | --- |
| `pydantic_ai_agents.unsessioned_traces` | trace-level; this fixture strips trace ids, so only `ai_classifier_corpus_test.rs` asserts it — and that needs `TRACE_CAPTURE_DIR`, which **no CI workflow sets** (the corpus lives in the other repo). Local-only. |
| `pydantic_ai_agents.key_state_by_candidate` | **none.** Not emitted into `expectations.json` at all. |

Both sit on the PROVISIONAL P1 ruling, so revisiting it should start by giving them
a gate.

If a golden looks wrong, re-review the seed per trace-capture's
`frameworks/REVIEW_IMPLEMENTATION.md`. Do **not** regenerate it from this
classifier's output — for the four marked entries in particular that would turn the
gate into "the classifier agrees with itself", with no file in either repo
recording that it happened.
